## Documento 15 (incluye completo el documento 14) — literal
Exacto. En una fábrica de UI/frontend, con 300 componentes, el agente no debería elegir 1 componente. Debe elegir un conjunto coordinado de componentes y construir un pequeño workflow para esa tarea.
Por ejemplo, si pides: "Crea un dashboard móvil con sidebar, tabla, filtros, gráficos y persistencia" el agente podría necesitar 15–30 componentes distintos:
OBJETIVO "Dashboard móvil completo" ↓ DESCOMPONER ↓ [layout · navegación · tablas · formularios · charts · responsive · estado · persistencia · accesibilidad · QA] ↓ BUSCAR COMPONENTES ↓ Layout/Grid · Sidebar · Navbar · Table · Pagination · Select · Search · DatePicker · Chart · Modal · Toast · Store · Persistence · Mobile viewport · Visual QA ... ↓ COMPOSICIÓN ↓ WORKFLOW UI
La clave sería que los 300 componentes estén catalogados por capacidad, no como una lista plana.
FÁBRICA UI — 300 COMPONENTES
01 LAYOUT (grid, flex, split-pane, responsive containers) · 02 NAVIGATION (sidebar, navbar, tabs, breadcrumb) · 03 DATA (table, tree, pagination, virtual list) · 04 INPUT (input, select, datepicker, upload, rich editor) · 05 VISUALIZATION (charts, diagrams, canvas) · 06 STATE (store, cache, persistence) · 07 EFFECTS (modal, toast, animations) · 08 QA (browser, screenshot, mobile, accessibility, visual diff)
Entonces DeepSeek trabaja en capas. Primero decide qué capacidades necesita: "crear editor visual" → canvas → drag/drop → resize → selection → layers → properties → undo/redo → persistence → keyboard → mobile touch → QA
Después el router busca varios candidatos para cada capacidad: drag/drop ├─ component-028 ├─ component-074 └─ component-192 · state ├─ component-051 └─ component-117 · canvas ├─ component-009 ├─ component-083 └─ component-220
Y DeepSeek no selecciona uno globalmente, sino: CAPABILITY PLAN canvas → C009 · drag/drop → C074 · resize → C081 · selection → C093 · layers → C105 · properties → C112 · undo/redo → C140 · persistence → C162 · mobile touch → C211 · QA → C281 + C287
Después viene una capa todavía más importante: compatibilidad. No basta con que cada componente sea bueno por separado. El router debe saber:
component: C074 / provides: [drag_drop] / requires: [react, dom] / compatible_with: [C009, C081, C093] / conflicts_with: [C192] / outputs: [drag_event, position_state]
Así el sistema puede evitar: componente A + componente B = 💥 incompatibles y preferir: A + C + D = PASS
Para tu fábrica yo usaría este flujo: PROMPT ↓ 1. UI PLANNER ¿qué capacidades necesita? ↓ 2. CAPABILITY ROUTER ¿qué componentes existen para cada capacidad? ↓ 3. COMPOSER elige varios componentes compatibles ↓ 4. DAG BUILDER decide orden y conexiones ↓ 5. CODE AGENT integra código ↓ 6. BUILD ↓ 7. BROWSER QA ↓ 8. VISUAL QA ↓ 9. VERIFIER ↓ PASS? ├─ NO → reemplazar/reconfigurar componente └─ SÍ → guardar receta
Lo potente es guardar la combinación que funcionó. Ejemplo: RECIPE: editor_visual_v1 = C009 canvas + C074 dragdrop + C081 resize + C093 selection + C105 layers + C112 properties + C140 history + C162 persistence + C211 touch + C281 browser-QA
La próxima vez que alguien pida algo parecido: "haz un editor visual" no empiezas buscando entre 300 otra vez. INPUT ↓ Recipe match ↓ editor_visual_v1 ↓ reutilizar 10 componentes ↓ adaptar únicamente diferencias. Eso también ahorra muchísimo en tokens.
En tu caso yo no lo llamaría simplemente Tool Router. Sería algo más parecido a: UI COMPONENT FABRIC — Registry ↓ Capability Graph ↓ Compatibility Graph ↓ Recipe Library ↓ Composer ↓ DAG ↓ Agent ↓ QA
Y así tus 300 componentes dejan de ser 300 tools que la IA debe recordar y se convierten en una biblioteca de piezas que el agente puede ensamblar, exactamente como una fábrica.

Para que ningún componente pase desapercibido, no dejaría la selección solo a DeepSeek ni solo a una búsqueda semántica. Pondría una capa de cobertura obligatoria.
300 COMPONENTES ↓ INVENTARIO ÚNICO OBLIGATORIO ↓ cada componente tiene: ID + capacidades + tags + entradas + salidas + compatibilidades + restricciones + estado de uso ↓ PLAN DE UI ↓ búsqueda por varias rutas ↓ candidatos combinados ↓ auditoría de cobertura ↓ composición final
Lo importante es que un componente pueda aparecer por más de una vía. Por ejemplo: C211 capacidades: [touch, drag, mobile, pointer-events] categorías: [interaction, mobile, editor] relacionado: [canvas, drag-drop, resize]. Aunque una búsqueda por "drag/drop" no lo encuentre, otra por "mobile", "touch" o por relación con el canvas lo recupera.
Yo usaría 5 defensas:
1. Registro 100% obligatorio. Ningún componente entra a la fábrica si no está en component_registry. El sistema compara físicamente las carpetas existentes contra el registro. Si existen 300 carpetas pero solo 298 registros: FAIL 2 COMPONENTES SIN INDEXAR
2. Búsqueda múltiple, no una sola. TAREA ↓ búsqueda por capacidad + búsqueda semántica + tags + dependencias + componentes relacionados + recetas históricas. Luego unes los resultados.
3. Coverage Matrix. Primero el Planner determina todas las capacidades necesarias: EDITOR UI [x] canvas [x] drag [x] resize [x] selection [x] layers [x] properties [x] undo [x] persistence [x] desktop [x] mobile touch [x] QA. Antes de empezar a programar, cada capacidad tiene que tener al menos un componente candidato. Si aparece: mobile touch → 0 candidatos el sistema no continúa. Vuelve a buscar en los 300.
4. Exploration quota. No elegir siempre los mismos 10 componentes porque ya funcionaron antes. Por ejemplo: 80% candidatos conocidos 20% candidatos poco usados/nuevos. Eso hace que componentes buenos que todavía no tienen historial tengan oportunidad de entrar.
5. Auditoría final de descarte. El sistema conserva por qué no eligió cada candidato: C074 → seleccionado · C081 → seleccionado · C092 → descartado: duplicado · C118 → descartado: incompatible React version · C211 → seleccionado para touch · C244 → descartado: solo desktop. Así un componente no desaparece silenciosamente.
Para tus 300 yo añadiría además un contador: COMPONENT HEALTH C001 → usado 42 veces · C002 → usado 13 veces · C003 → nunca evaluado ⚠ · C004 → evaluado, nunca seleccionado · ... · C300 → usado 2 veces. Y una cola automática: UNSEEN / UNDERUSED COMPONENTS C003 C027 C119 C283. Cada cierto número de trabajos, el router fuerza una reevaluación de esos componentes cuando sean compatibles.
El flujo completo quedaría: 300 componentes ↓ INVENTORY CHECK ¿están registrados los 300? ↓ UI PLANNER define capacidades ↓ MULTI-SEARCH semántica + tags + graph + dependencies ↓ CANDIDATE SET 20–40 componentes ↓ COVERAGE CHECK ¿todas las capacidades tienen candidatos? ↓ COMPATIBILITY CHECK ↓ DeepSeek compone 10–25 componentes ↓ QA ↓ AUDITOR ¿hubo componentes relevantes ignorados? ↓ PASS / REPLAN
La regla que pondría en YAIWES sería muy simple: > Ningún componente puede quedar invisible: todo componente debe estar indexado, ser recuperable por múltiples rutas y tener trazabilidad de cuándo fue evaluado y por qué fue seleccionado o descartado.
Así puedes tener 300, 500 o 2.000 componentes sin depender de que la LLM "se acuerde" de ellos.

Sí. Esa es justamente la evolución correcta: copiar de Hermes/OpenClaw la idea de descubrir capacidades bajo demanda, pero sustituir el "skill que la IA debe leer y recordar" por un contrato ejecutable que el runtime obliga a cumplir.
Hermes / OpenClaw: INPUT ↓ buscar skills ↓ leer descripción ↓ inyectar SKILL.md ↓ LLM interpreta ↓ LLM intenta usarlo
FÁBRICA UI YAIWES: INPUT ↓ motor determinista ↓ buscar CAPACIDADES ↓ resolver componentes ↓ cargar Schema/Contract ↓ construir Workflow/DAG ↓ inyectar SOLO interfaces necesarias ↓ ejecutar CODE REAL
La diferencia es importante: la LLM ya no tiene que acordarse de ejecutar un skill.
Por ejemplo, en vez de esto: SKILL.md "Cuando necesites drag/drop, usa esta librería y haz..." tendrías algo ejecutable:
id: ui.dragdrop.core / provides: [drag, drop, reorder] / requires: [dom, pointer_events] / inputs: {target: ComponentTree, canvas: CanvasState} / outputs: {state: CanvasState, events: DragEvents} / executor: {module: runtime/dragdrop, entrypoint: execute} / tests: [desktop, touch] / compatible_with: [ui.canvas, ui.selection, ui.layers]
Entonces el runtime puede hacer realmente: resolver("drag_drop") ↓ ui.dragdrop.core ↓ load() ↓ execute(...). No depende de que DeepSeek decida escribir correctamente el código para invocarlo.
Lo que copiaría de Hermes/OpenClaw: Mantendría el concepto: NO cargar 300 componentes ↓ descubrir qué hace falta ↓ cargar únicamente lo necesario. Pero cambiaría el objeto cargado: ANTES Skill = instrucciones para la IA / YAIWES Capability = contrato + schema + código + tests
Incluso puedes tener una descripción minúscula para descubrimiento: id: ui.touch.coordinates / summary: Corrige interacción táctil y coordenadas móviles. / capabilities: [touch, pointer, coordinate-transform]. El motor lee eso. Solo después de elegirlo carga: schema, dependencies, executor, tests, adapter. Eso mantiene el contexto extremadamente pequeño.
Sí pondría un motor determinista interno. De hecho, con 300 componentes yo no dejaría a DeepSeek ser el router principal. Crearía algo como: YAIWES Capability Engine — INPUT ↓ REQUIREMENT PARSER ↓ CAPABILITY RESOLVER ↓ REGISTRY ↓ DEPENDENCY RESOLVER ↓ COMPATIBILITY ENGINE ↓ DAG BUILDER ↓ POLICY GATE ↓ EXECUTOR ↓ VERIFIER ↓ PASS / RETRY. Cada pieza puede funcionar principalmente con código determinista.
Por ejemplo: Usuario: "el drag funciona con mouse pero falla en móvil" ↓ Requirement Engine required: [drag_drop, touch, pointer_coordinates, mobile, regression_test] ↓ Capability Resolver C074 dragdrop · C211 touch · C219 coordinate-normalizer · C281 mobile-browser · C287 regression-runner ↓ Dependency Solver C074 ├─ C211 └─ C219 ↓ C281 ↓ C287 ↓ DAG ejecutable. DeepSeek no necesita inventar esa estructura desde cero.
¿Dónde entra entonces la LLM? Solo donde realmente aporta inteligencia: DETERMINISTA (buscar componentes, resolver dependencias, validar schemas, controlar permisos, ejecutar DAG, verificar tests) → LLM (interpretar petición ambigua, diseñar cambio nuevo, escribir/adaptar código, diagnosticar fallo complejo, proponer solución, razonar si QA falla). Es decir: LLM = razonamiento / ENGINE = control. No: LLM = razonamiento + memoria + scheduler + routing + dependencias + selección + ejecución + validación. Eso último es donde empiezas a gastar tokens a lo loco y aparecen errores.
Incluso el motor puede preparar el contexto para DeepSeek. Esto me parece especialmente bueno para tu Router. En lugar de: DeepSeek: "Aquí tienes 300 componentes. Decide." el motor entrega: TASK Fix mobile drag coordinates. REQUIRED CAPABILITIES [drag_drop, touch_input, coordinate_transform, mobile_test] SELECTED COMPONENTS [C074, C211, C219, C281] CURRENT STATE [desktop: PASS, mobile_touch: FAIL] AVAILABLE ACTIONS 1. inspect(C074) 2. inspect(C211) 3. patch(C219) 4. test(C281). DeepSeek recibe quizá 500–1500 tokens, no decenas de miles. Y sus decisiones están limitadas a acciones reales.
Workflow en lugar de Skill. Una vez que una combinación funciona: C074 + C211 + C219 + C281 + C287 la fábrica la compila como: workflow: mobile_drag_repair_v1 / steps: [inspect_pointer_state, normalize_coordinates, patch_drag_adapter, run_mobile_browser, run_touch_regression] / success: [touch_drag_pass, desktop_no_regression]. La próxima vez: "falló drag móvil" ↓ matcher ↓ mobile_drag_repair_v1 ↓ RUN. Quizá ni siquiera necesitas llamar a una LLM hasta que algún paso falle. Eso es muchísimo más potente que un skill.
Y también puedes tener POOLS. Los 300 componentes no tienen que convertirse todos en workflows. Puedes tener: TOOL una operación atómica · POOL grupo de componentes de una capacidad · WORKFLOW secuencia ejecutable · SERVICE motor persistente. Por ejemplo: POOL: frontend.mobile C201 viewport · C202 touch · C203 gesture · C204 pointer · C205 responsive · C206 orientation · C207 keyboard-mobile · C208 screenshot. El agente solicita: pool.require("frontend.mobile") y el motor decide qué miembros concretos necesita.
La pieza central sería un "compiler". PETICIÓN HUMANA ↓ INTENT ↓ REQUIREMENT SCHEMA ↓ CAPABILITY GRAPH ↓ COMPONENT GRAPH ↓ EXECUTION DAG ↓ CODE. Por ejemplo: "Crea editor visual móvil" se compila a: Canvas · Selection · DragDrop · Resize · Layers · Properties · History · Persistence · Touch · Responsive · VisualQA y eso se compila a componentes concretos.
Regla importante: La LLM nunca debería poder "ignorar" una dependencia obligatoria. Si: DragDrop.requires: TouchAdapter el DAG Builder agrega automáticamente: TouchAdapter aunque DeepSeek no lo haya mencionado. Lo mismo para: requires, conflicts, provides, permissions, tests, inputs, outputs. Eso es exactamente para lo que sirve el motor determinista.
Arquitectura final: CHAT ↓ Router YAIWES ↓ Requirement Compiler ↓ CAPABILITY ENGINE ├─ Registry (300 comps) ├─ Dependency Graph (Compatibility) └─ Recipes (Workflows) ↓ DAG Builder ↓ Contract Gate ↓ CODE EXECUTOR determinista + DeepSeek solo cuando hace falta ↓ QA ↓ Verifier ↓ PASS / REPLAN
Así conservarías de Hermes/OpenClaw lo bueno de "descubrir e inyectar solo lo necesario", pero YAIWES subiría un nivel: no inyecta instrucciones esperando que la IA obedezca; inyecta contratos y capacidades cuyo código está registrado y puede ejecutarse obligatoriamente. Y tu idea del motor determinista es especialmente importante: debería ser el control plane, mientras DeepSeek funciona como el razonador dentro de límites definidos por ese control plane.

## Documento 16 (= documento 19) — literal
Sí. Ahí conviene separar dos clases de componentes, porque no deben integrarse igual.
1. Software determinista: no necesita LLM. Ejemplos: motor de drag/drop, parser HTML, generador CSS, sistema de undo/redo, validador, exportador JSON, screenshot, formatter, compiler, gestor de archivos. Ese software ya sabe exactamente qué hacer: resize(node, width, height) · export_html(project) · undo() · save_project() · validate_css(). No necesitas que DeepSeek "razone" dentro de ese componente. Con CLI-Anything, la idea sería envolver su API/código real: SOFTWARE ORIGINAL ↓ CLI-Anything ↓ Agent Harness ↓ comandos estructurados: ui resize --node button-42 --width 180 · ui move --node card-7 --x 200 --y 90 · ui export --format html. Después tu runtime YAIWES registra esos comandos como acciones ejecutables: Tool: ui.resize · Tool: ui.move · Tool: ui.export. DeepSeek solamente decide cuándo llamar a cada uno.
2. Software de diseño/editor: puede contener muchas funciones internas. Por ejemplo, un editor visual podría tener: CANVAS, LAYERS, DRAG/DROP, RESIZE, ALIGN, SNAP, TEXT, IMAGE, COLOR, COMPONENT LIBRARY, UNDO/REDO, EXPORT. No lo convertiría en un único tool = editor. CLI-Anything debería descubrir/envolver sus entrypoints y producir algo parecido a: POOL: visual_editor ├─ canvas.create ├─ component.insert ├─ component.move ├─ component.resize ├─ component.delete ├─ style.set ├─ layer.reorder ├─ history.undo ├─ history.redo ├─ project.save └─ project.export. Entonces DeepSeek dispone de un pool programático completo.
¿Cómo trabaja DeepSeek con eso? Imagina que dices: > Crea una tarjeta con imagen, título y botón y colócala en dos columnas. El flujo sería: PROMPT ↓ DeepSeek ↓ PLAN ESTRUCTURADO 1 crear layout 2 insertar card 3 insertar image 4 insertar text 5 insertar button 6 aplicar estilos 7 revisar resultado ↓ Capability Engine ↓ busca ejecutores reales ↓ visual_editor.create_grid · visual_editor.insert_component · visual_editor.set_style · visual_editor.align · browser.screenshot ↓ CODE REAL. DeepSeek no dibuja imaginariamente. Está programando el editor mediante sus funciones reales.
CLI-Anything sería el traductor. La función de CLI-Anything en tu fábrica sería algo así: SOFTWARE OSS (GrapesJS, Konva, Fabric, editor X, motor Y) ↓ CLI-ANYTHING "¿Qué puede hacer realmente este software?" ↓ HARNESS create_canvas() insert_component() move_component() set_property() export_project(). Y después tu sistema transforma ese harness en: SCHEMA + TOOLS + POOL + WORKFLOWS. No necesitas conservar SKILL.md como mecanismo principal.
El Schema le dice al agente cómo llamar al código. Por ejemplo: id: ui.component.resize / executor: {module: visual_editor, function: resize_component} / input: {component_id: string, width: number, height: number} / output: {component_id: string, bounds: object, success: boolean}. DeepSeek recibe solamente: ui.component.resize(component_id, width, height). No necesita leer 3.000 líneas del componente.
Y los workflows eliminan todavía más decisiones LLM. Supongamos que tienes un software que ya sabe construir un formulario. En lugar de obligar a DeepSeek a ejecutar: create input, create label, create select, create button, align, space, style, validate guardas: WORKFLOW: form.standard.create. Por debajo: create_form ↓ create_fields ↓ layout ↓ style ↓ validation ↓ responsive. Entonces DeepSeek simplemente ordena: run workflow form.standard.create y el código hace los ocho pasos. Esto reduce muchísimo tokens y errores.
Para software de edición/diseño hay una ventaja adicional. Puedes hacer un LOOP de ejecución real: DeepSeek ↓ "mueve botón" ↓ Editor Harness ↓ move(button, x, y) ↓ Canvas real cambia ↓ Screenshot ↓ modelo visión / verifier ↓ ¿correcto? ├─ SÍ → continúa └─ NO → corrige. Así tu agente puede diseñar visualmente usando software real, en vez de generar CSS a ciegas.
Yo organizaría tus 300 componentes así: 300 COMPONENTES │ ├── SOFTWARE (editor, canvas, renderer, browser, exporter, compiler) ├── TOOLS (funciones atómicas) ├── POOLS (familias de funciones) └── WORKFLOWS (procesos ya ensamblados). Y encima: DeepSeek Harness ↓ Capability Engine ↓ Schema / Contracts ↓ TOOL · POOL · WORKFLOW ↓ SOFTWARE REAL
La regla clave: DeepSeek decide intención y composición. El motor determinista resuelve dependencias. CLI-Anything convierte software en una interfaz programable. El software real ejecuta el trabajo. Así incluso un componente que no tiene ninguna IA puede convertirse en una capacidad nativa extremadamente útil para el agente.

Y los motores pueden trabajar en paralelo: REQUEST ↓ REQUIREMENT ENGINE ↓ DAG BUILDER ↓ CANVAS · SCHEMA · STYLE · DATA · ACTION ENGINES ↓ COMPOSER ↓ PREVIEW ENGINE ↓ VISUAL QA · INTERACTION QA · TEST ↓ VERIFIER.
Cómo lo programaría: un contrato común de motor: class Engine: id: str; capabilities: list[str]; async def can_handle(self, task); async def execute(self, task, context); async def verify(self, result). Cada motor lo implementa (LayoutEngine id "ui.layout", CanvasEngine "ui.canvas", VisualQAEngine "qa.visual", PackagingEngine "build.package"). ENGINE_REGISTRY = {"ui.canvas", "ui.layout", "ui.style", "ui.schema", "ui.actions", "code.sandbox", "qa.visual", "qa.interaction", "build.package"}. El DAG puede pedir varios simultáneamente con asyncio.gather(...). Tus documentos ya proponen pool persistente, prioridad, caché, batching, pipelines async y deduplicación.
Dónde pondría DeepSeek: no encima de cada microacción. DeepSeek Harness (interpretar + planificar) ↓ DAG / CONTRACT ↓ DETERMINISTIC ENGINE BUS (Canvas, Layout, Style, Schema, Actions ...) ↓ RESULT ↓ DeepSeek solo si: algo nuevo / fallo / conflicto. De 100 operaciones, quizá 80–95 podrían ser ejecución de código determinista.
Y CLI-Anything entraría como una fábrica de adaptadores: SOFTWARE OSS existente ↓ CLI-Anything ↓ Harness ejecutable ↓ ENGINE ADAPTER ↓ ENGINE_REGISTRY. Ejemplo: GrapesJS ↓ CLI-Anything / adapter ↓ canvas.create, canvas.insert, canvas.move, canvas.resize, canvas.export ↓ CANVAS_ENGINE. Eso evita convertir tus cientos de componentes en cientos de "skills". Se convierten en motores + tools + pools + workflows ejecutables.
La primera implementación que haría en esa raíz sería solo 6 motores base: Capability, Canvas, Layout, Action/Flow, Sandbox y QA. Después añadiría Style, Schema, Persistence y Packaging. Con esos seis ya puedes probar el concepto sin rediseñar toda la fábrica.
